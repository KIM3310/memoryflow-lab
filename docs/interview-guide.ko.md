# 반나절 심층면접 방어 가이드

## 30초 설명

MemoryFlow Lab은 LLM 장문맥 추론에서 모델 가중치와 KV cache가 HBM 용량을 넘을 때, HBM-only·원격 메모리 tiering·near-memory 방식을 동일 조건에서 비교하는 재현 가능한 시뮬레이터입니다. 단순 속도 예측보다 먼저 용량 가능성을 판정하고, KV 이동량과 노출 지연을 토큰별로 계산해 어떤 가정에서 결론이 바뀌는지 보여줍니다.

## 반드시 직접 설명할 수 있어야 하는 식

```text
KV bytes/token/sequence = 2 * layers * kv_heads * head_dim * bits / 8
```

- `2`: key와 value
- `kv_heads`: GQA에서는 전체 attention head 수와 다름
- 전체 KV: 위 값 × sequence length × concurrent sequences

## 예상 질문과 답변

### 왜 HBM-only가 가장 빠르다고 비교하지 않았나요?

용량을 넘는 구성은 속도 비교 대상이 아니기 때문입니다. 먼저 가중치를 빼고 남은 HBM에 KV가 들어가는지 판정했습니다.

### CXL을 쓰면 무조건 처리량이 늘어나나요?

아닙니다. 수용 가능한 동시 요청 수는 늘 수 있지만, attention 단계에서 cold KV를 반복 이동하면 지연이 커집니다. 그래서 용량과 지연을 동시에 봐야 합니다.

### near-memory가 무조건 낫다는 결론인가요?

아닙니다. 현재는 이동량 감소율을 매개변수로 둔 proxy입니다. 실제 판단에는 PIM 연산 처리량, bank conflict, compiler 지원, 동기화 비용, 전력·열, 실측값이 필요합니다.

### 왜 cycle-accurate simulator를 바로 쓰지 않았나요?

첫 단계의 목적은 불가능한 구성을 빠르게 제거하고 민감 변수를 찾는 것입니다. 다음 단계에서 Ramulator나 하드웨어 카운터로 보정할 대상을 좁히기 위한 모델입니다.

### AI가 대부분 작성했다면 본인 역량은 무엇인가요?

AI는 구현 속도를 높였지만 문제 정의, 비교 기준, 식과 단위, 실패 조건, 검증 속성, 과장 방지 경계는 제가 소유합니다. 면접에서는 임의 입력을 바꿔 결과가 왜 달라지는지 코드와 식으로 설명하고, 잘못된 가정은 즉시 수정할 수 있어야 합니다.

## 현장 과제 대응 순서

1. 목표 지표와 제약을 분리한다.
2. 단위를 먼저 적는다.
3. 불가능한 구성을 capacity gate로 제거한다.
4. 가장 단순한 baseline을 만든다.
5. 한 번에 변수 하나만 바꾼다.
6. 결과보다 반례와 한계를 먼저 말한다.
7. 다음 실측 계획을 제안한다.
